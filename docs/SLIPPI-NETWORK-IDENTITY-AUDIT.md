# Slippi account and networking audit

Date: 2026-09-10. Status: offline due diligence; public Slippi support disabled.

## Product decision

The intended MeleePad entry points are **Play Melee** and **Play Online with
Slippi**. The online path must use the player's own Slippi account. First prove
Direct against an arranged desktop opponent, then Unranked matchmaking. Ranked
is later scope. Do not expose a working-looking online button before its
runtime, account handoff and failure handling work.

The inspected Slippi protocol has matchmaking queues and Direct connect codes;
it does not establish an API for browsing every online player. Direct-code
history is local history, not a live player directory. A player browser should
only be offered if a supported upstream discovery surface is established.
The [official launcher](https://github.com/project-slippi/slippi-launcher)
provides the existing Slippi entry point. Its development mocks are not live
accounts; production launcher integration may require upstream API access.

## Available account for acceptance testing

The owner supplied their Slippi profile and authorized using their normal
signed-in account for testing. Browser inspection confirmed a signed-in
session. No connect code was changed, no credential file was downloaded, and
no native client authenticated or entered a live queue in this pass.

Subsequent official-client preparation opened Slippi Launcher 2.15.1 and
observed the owner's signed-in main screen. The unmodified desktop Slippi 3.6.4
client also opens. No credential file was copied into the probe, and neither
official-client game boot nor a crossplay match is verified. See
[desktop readiness](artifacts/slippi-feasibility-2026-09-10/official-desktop-readiness.json).

The existing [online enable page](https://slippi.gg/online/enable) explicitly
labels its flow outdated and directs users to sign in through Slippi Launcher.
Use the supported Launcher route when preparing desktop acceptance. Browser
login alone does not establish an iOS credential handoff. Keep the supplied
profile identifier and any eventual credentials out of test fixtures, source,
public evidence and packaged apps. Accepted gameplay tests use synthetic
accounts on loopback or the guarded private LAN. The separate Direct candidate
has no synthetic account or fixture transport and has not made a service request.

The private `ios-direct-002` candidate now implements document-picker account
import, device-only Keychain storage and a temporary 0600 runtime credential
copy. Its setup screen is installed and visually verified on the physical iPad.
The 21 account helper checks and 13 Direct restriction checks pass, but actual
document import, Keychain operation on the device, service authentication and
crossplay remain untested. It cannot enter Unranked or Ranked through the
guarded game search path. See [Direct candidate evidence](artifacts/slippi-feasibility-2026-09-10/direct-candidate.json).

The subsequent **ios-direct-003** wired-import test now verifies device Keychain
storage/readback, actual runtime account-file loading, no-JIT menu boot, clean
shutdown, and removal of the two temporary plaintext copies. The credential
came from the owner's existing official Launcher login with explicit permission;
no values were printed or packaged. Matchmaking play-key acceptance and a
distinct-account desktop match remain untested. [Physical account result](artifacts/slippi-feasibility-2026-09-10/ipad-real-account-boot.json).

## What identifies a player

Audited donor revisions: modern Dolphin
`41a7a3a110ed52999486ae1901c8fbb9a63d4f13`, Rust extensions
`2d29e794de8497582675fb70877851f2cdd2f256`.

| Value | Meaning and handling |
|---|---|
| Account UID | Slippi account identity. Obtained through the normal account flow, never generated by MeleePad or bundled as a default. |
| Play key | Account credential. Never bundle, log, publish, share across users, or put into a URL. The private Direct candidate's wired Keychain import and temporary upstream file handoff passed on-device; matchmaking acceptance remains untested. |
| Connect code/display name | Account-facing identifiers. Read from the current account; a connect code is not an authentication secret. |
| App version, bundle ID, game revision | Expected to be common across users. These are compatibility/application identifiers, not individual player accounts. |
| Match ID | Returned by matchmaking. Scope results and reports to this match and its participants; do not invent or reuse a stale ID. |
| UDP port/ENet connection ID | Transport state. Ports may repeat on different hosts; they are not account identities or globally unique user IDs. |
| Diagnostic run UUID | Local test-folder separation only. It is not a Slippi account or credential. |

The [ticket construction and transport](https://github.com/project-slippi/dolphin/blob/41a7a3a110ed52999486ae1901c8fbb9a63d4f13/Source/Core/Core/Slippi/SlippiMatchmaking.cpp)
send `uid`, `playKey`, `connectCode`, `displayName`, search settings, app version
and LAN address. No install UUID or hardware fingerprint is present in that
ticket. This finding is scoped to the inspected path, not every Slippi service.
One thousand copies of the same app version are normal; one thousand copies of
an operator's credential file would impersonate the same account.

## Executed account-isolation test

The new [Rust probe](../scripts/slippi-identity-probe.rs) links the existing
pinned Slippi UserManager libraries. It runs on macOS with OS-level networking
denied and synthetic account values only. It establishes:

- 1,000 independently constructed managers start anonymous and retain separate
  account state after being populated with distinct fixtures.
- Cloning a UserManager deliberately shares the same account. Use a new manager
  for a separate account context; cloning is appropriate for handles belonging
  to that same session.
- Copying the same synthetic `user.json` into two separate directories loads
  identical credentials. Different install folders do not fix copied identity.
- Logout clears shared handles for that account and deletes its credential file
  without deleting the second user's file or changing their identity.
- The real file loader reports success with network access denied. Local
  credentials loaded is therefore not evidence of successful server login.

This is **not** a 1,000-player network load test, account creation, or a guarantee
against service enforcement. No production account or matchmaking request was
sent. [Recorded result](artifacts/slippi-feasibility-2026-09-10/account-identity-isolation.json).

Reproduce using the existing accepted Rust build:

```sh
python3 scripts/probe-slippi-identity.py \
  --rust-build ref/slippi-compatibility/rust-build-macos-stable \
  --output ref/slippi-compatibility/identity-new
```

The [bundle guard](../scripts/audit-slippi-bundle-identity.py) now runs in the
private probe packager and public IPA packager. It rejects known account/history
files, nonempty credential fields in JSON/plist, unreadable metadata, and
symlinks requiring explicit review. Seven rejection fixtures and two accepted
fixtures pass. The current private probe passes inspection of 62 metadata
files. It still contains private game data and must not be distributed.
This guard does not detect every possible secret embedded in arbitrary binary,
INI, or obfuscated content; release review and clean build inputs remain needed.

## Networking findings requiring implementation or acceptance

1. **Credential transport:** in this pinned donor, matchmaking serializes the
   play key into JSON and sends it through ordinary ENet reliable packets.
   No TLS/DTLS layer is visible in that path. ENet reliability is not encryption.
   User-information and reporting HTTP paths use HTTPS, which does not protect
   this separate ticket path. Resolve the supported upstream transport contract
   before public account integration; do not invent a private protocol change
   that the service cannot understand.
2. **iOS sign-in:** the legacy browser flow passes a desktop `user.json` path to
   the Slippi site. It does not provide a proven iOS sandbox handoff. Implement
   an upstream-compatible per-user flow, validate incoming data, and bridge
   Keychain-held credentials into the runtime without distributing a seed file.
   Distinguish signed out, saved account loaded, connecting, service accepted,
   expired/rejected credentials and offline states.
3. **Session ownership:** leave a queue/end a connection before account switch.
   Bind reports to the account and match that created them; cancel stale
   callbacks rather than applying them to a newly signed-in user. The donor
   status reporter snapshots the current account when a report is enqueued;
   this is not yet a tested lifecycle for MeleePad account switching.
4. **Diagnostics:** donor logging includes LAN/peer addresses, ports, match IDs
   and whole unexpected matchmaking responses. Replace public diagnostics with
   an allowlist of redacted event types and timings. Never export play keys,
   account files or unfiltered response bodies.
5. **NAT and connection lifecycle:** test two players behind the same public IP,
   distinct home networks, restrictive NAT, port changes, background/resume,
   disconnect/reconnect and stale packets. The donor peer path deliberately
   tolerates changed source ports and has host-only matching in a connection
   fallback; multi-peer same-NAT behavior needs acceptance. This is not proof of
   a vulnerability, but account uniqueness alone cannot prove correct routing.
6. **IPv6 and retries:** the Rust API client currently filters DNS results to
   IPv4. Test iOS IPv6-only/NAT64 and cellular rather than assume availability.
   Audit queue cancellation and bounded backoff under service failure; do not
   repeatedly retry rejected credentials. The current development version
   selects a development matchmaking host; it is not a production-qualified
   release. Do not spoof a supported version to bypass checks.

## Release gate

Continue the compatibility port. Do not ship a shared demo account, introduce
hardware fingerprinting, rotate identifiers to evade restrictions, or promise
that accounts cannot be banned. Public enablement requires the account and
network lifecycle above, a full desktop Direct match/results/rematch, acceptable
sustained iPad performance and an actual Unranked game. Offline correction and
account-isolation passes are useful prerequisites, not substitutes.
