- The fix is incomplete as a class. PPC_OP_FRSP still emits ctx->fpr[d] = (f64)(f32)ctx->fpr[d]; only (emitter.c:1082) at 1,237 sites in the corrected module, while Dolphin fills both lanes and GXRuntime's ppc_frsp exists and is already used by the LLVM lowering (llvm_runtime_lowering.cpp:260-262). frsp before psq_st is a classic Gekko idiom; this can keep producing the same warping. That the long lockstep boot didn't flag it is not exculpatory — frsp targets often already hold an equal ps1 from a prior single op, so divergence is data-dependent.
- Lanes: compute in double from ps0 operands; round to single; write the rounded value (as f64) to both ps0 and ps1.
- Rounding: ForceSingle — with FPSCR.NI set, a result whose pre-rounding magnitude is below the smallest normal single flushes to signed zero (Melee runs with NI set, so this quirk is live).
- fmuls: the C operand is first rounded with Force25Bit (round-to-nearest at mantissa bit 25, subnormal-aware); after the write, FPSCR.FI and FPSCR.FR are cleared (& ~0x00060000).
- NaN policy: SNaN operand → VXSNAN + FX; result is the quietened first NaN operand (a-then-b/c order); no-NaN-operand invalids produce PPC_NAN with VXISI (inf−inf), VXIMZ (0×inf), VXZDZ (0/0), VXIDI (inf/inf); FI/FR cleared on NaN paths.
- fdivs: divisor 0 → ZX; with ZE=1 the destination and FPRF are not written.
- Enabled invalid (VE=1): destination and FPRF not written; FPSCR exception/FX bits still set.
- FPRF: 5-bit single-precision classification written on every successful result.
- Rc=1: CR1 ← FPSCR[FX,FEX,VX,OX]. The emitter emits no CR1 update for these four ops — acceptable for GALE01 rev0 (zero Rc=1 sites, verified), but a decoder-level assert or emit_set_cr1_from_fpscr call should close it.
GXRuntime's cpu_interpreter_float.c already implements all of this. Note that DolRecomp's test runtime (src/cpu/cpu.c:1291-1306) is a second, weaker implementation (no NI flush, no VE/ZE gating, no NaN policy) — the regression suite validates lanes, not exact semantics.
Keep the helper-call emission — it is the right design. The profile-free corrected build already compiles each ppc_f*s into a self-contained straight-line leaf, and its 45–48 FPS matches the old wrong code's profile-free numbers, i.e. the exact semantics are approximately free once the build is healthy. Do not inline full semantics at 17,700 sites (≈ +100 instructions × 17,700 sites of icache pressure; LLVM already declines this inline even unprofiled, for good reason). Concretely:
1. Keep ppc_fadds/fsubs/fmuls/fdivs(ctx, d, a, b/c) emission as in the current diff.
2. Also route PPC_OP_FRSP through ppc_frsp (exists in GXRuntime and in the LLVM lowering; DolRecomp's test runtime has it at cpu.c:1329). This also fixes frsp's missing SNaN/FPRF behavior and restores C/LLVM backend parity.
3. In cpu_interpreter_float.c, make the helpers profile-robust leaves: mark ni_add/ni_sub/ni_mul/ni_div, force_single, force_25bit_c, fp_write_single, classify_f32, set_fprf static inline __attribute__((always_inline)) (or move to a shared private header). This guarantees the good profile-free code shape regardless of what any stale or partial profile says, killing the observed PGO body degradation (frame + bl _ni_add per op) permanently.
4. Retrain PGO from the corrected source before any retention decision — mandatory anyway, since the emitter change makes every old profile stale with respect to the new hot path.
5. Add emit_set_cr1_from_fpscr on inst->rc for the four ops (or a decode-time hard error), so the gap can't bite a different title/revision later.
Do not take the "assign both lanes inline, skip FPSCR" shortcut (question 4). It would fix the visual defect but retain a genuine numeric divergence — fmuls without Force25Bit produces different ps0 results from hardware/Dolphin whenever C has low mantissa bits, which breaks lockstep, replay determinism, and eventually G9 netplay sync, and would silently diverge from the LLVM backend, which already calls the exact helpers. Given the evidence that exact helpers are performance-neutral profile-free, the shortcut buys nothing measurable.
Three stacked causes, in decreasing confidence:
1. Confirmed: the profile (fountain2-fd1.profdata) has no records for the runtime FP helpers (trained when generated code never called them). Under -fprofile-instr-use, unprofiled functions get pessimized treatment: in the PGO build, ni_add is no longer inlined into ppc_fadds, which gains a full stack frame and a second call per guest FP instruction, and unprofiled runtime code is laid out/optimized as cold. This is a real per-op regression multiplied by millions of ops per frame.
2. Not the cause: call-site inlining. Both builds leave the vast majority of the 17,700 sites as out-of-line calls; PGO did not change that.
3. Unquantified confound: the 12–15 FPS and 45–48 FPS observations came from different four-player scenes, and the corrected-PGO module's own capture shows 51.1 FPS on Fountain. Part of the "collapse" may be scene selection. The profile-hash silence is expected, by the way — replacing straight-line inline arithmetic with straight-line calls does not change clang's CFG-based function hash, so callers' profiles applied cleanly; nothing was "misleading despite no warning" beyond the missing helper records.
